# Patient data export

Verified 17 October 2026: the backend build passed with zero warnings/errors, and the complete suite passed 206/206 tests with no skips (131 non-SQL, 75 SQL). Export coverage includes 14 unit cases and three SQL HTTP cases. Evidence is in [verified.trx](../.artifacts/backend-tests/verified.trx). These local results do not establish production acceptance.

`GET /api/privacy/export` retains the existing JSON response envelope and top-level keys. Additional sections include owned intake, appointment history, dated consultation/report notes, published plan history, progress correction history, adherence, invoices, refunds and data-rights requests. Provider responses, payment/meeting tokens, host links, credentials, security stamps and unpublished plan snapshots are excluded through explicit projections.

`GET /api/privacy/export/bundle` is available only to the signed-in Patient and accepts no owner ID. It completes a ZIP before returning a file response. The ZIP contains `records.json`, `manifest.json`, and owned report/message files under generated numeric-ID paths. The manifest records actual sizes and SHA-256 hashes, including a hash of `records.json`. Original filenames are display metadata; they do not determine archive paths. Downloads use `application/zip`, an attachment filename, `no-store` and `nosniff`.

The agreed data-rights rule permits a patient to export their own historic report files and sent/received message attachments after clinician assignment or chat contact revocation. Current clinician relationship checks do not gate this self export. This grants no clinician or administrator access to another person's bundle. Existing clinical/attachment endpoints retain their separate permissions.

Every file requires both an owned database row and its expected upload prefix: `patients/{patientId}/medical-reports/` or `chat/{min(senderId,receiverId)}-{max(...)}/`. Absolute URLs, traversal, mismatched ownership prefixes and ambiguous legacy attachment references are rejected. The exporter never fetches a URL. Foreign rows are excluded before storage access. Retained soft-deleted report/message metadata appears in separate `retainedReports` / `retainedMessages` sections and its still-held private bytes are included; the old active-record lists retain their meaning. This performs no deletion and establishes no retention period.

The bundle uses sequential private storage streams and a random temporary ZIP in the API content root's `.local/private-exports` directory, outside the static web root. Unix files/directories are created for the service user only; deployment must also restrict the directory's Windows/server filesystem ACL to the service account. File streams use `DeleteOnClose`; failures, cancellation and response disposal release the file and concurrency lease. The process-wide lease remains held while the completed download stream is open. The service resolves storage lazily, so JSON-only export does not require a working file provider.

Default `PrivacyExport` settings are `MaxConcurrentExports: 2`, `MaxFiles: 200`, `MaxRecords: 20000`, `MaxRecordBytes: 10485760`, `MaxFileBytes: 10485760`, `MaxTotalFileBytes: 262144000`, `MaxArchiveBytes: 314572800`, and `TimeoutSeconds: 120`. Startup validates configuration bounds. Limits are technical resource safeguards, not a restriction on the underlying data-rights request process. Limits apply to actual copied bytes as well as available metadata. Missing files, inaccessible storage, mismatched file size, unsupported legacy references, exceeded limits or preparation timeout return an explicit `409` directing the patient to assisted export. No partial archive or silent truncation is returned.

The existing independent audit middleware records authenticated `/api/privacy` reads and outcomes without persisting file bytes or storage references. Records are read during preparation, with bounded counts/serialization size; this is not a database backup or an atomic historical snapshot. Storage objects are expected to remain immutable under their generated keys. Production file availability, deployment permissions and assisted-export handling remain operational acceptance inputs.

Root registration: import `NutriCare.API.Privacy` and call `services.AddPatientDataExport(configuration)` before building the host. No model or migration is needed for export.

All 14 `PatientDataExportTests` cases passed, covering owned/retained contents after revocation, hash integrity, foreign/draft/provider-secret exclusion, safe ZIP paths, forged/remote/traversal references, missing files, actual-byte/count/archive limits, cancellation cleanup and response-lifetime capacity. All three `SqlPatientDataExportHttpTests` cases passed using real JWT sessions and SQL, covering the bundle plus compatible JSON/audit, anonymous/Admin denial, and an audited missing-file `409`. Private file bytes in these tests came from a controlled test storage implementation; real storage-provider availability and deployment filesystem permissions still require operational verification. Full-stack staging journeys and clinician/Urdu translation acceptance are not claimed.
