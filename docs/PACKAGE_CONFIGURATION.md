# Configurable package proposals and clinician review

Verified 17 October 2026: the backend build passed with zero warnings/errors, and the complete suite passed 206/206 tests with no skips (131 non-SQL, 75 SQL). Package configuration coverage includes 15 unit cases, seven SQL cases and four enrollment SQL HTTP cases. Evidence is in [verified.trx](../.artifacts/backend-tests/verified.trx). These results do not publish proposals, enable checkout or establish production acceptance.

The proposed package terms are stored as separate, inactive drafts:

| Package | Days / PKR | Initial consultation | Follow-ups | Diet plans / revisions | Progress | Credit expiry |
| --- | --- | --- | --- | --- | --- | --- |
| Starter | 14 / 4000 | 1 × 45 minutes | 1 × 20 minutes | 1 / 0 | Basic | 14 days |
| Monthly | 28 / 7500 | 1 × 45 minutes | 3 × 20 minutes | 1 / 2 | Weekly | 28 days |
| Transformation | 84 / 18000 | 1 × 45 minutes | 11 × 20 minutes | 3 / 6 | Weekly | 84 days |

All proposals set a 30-day first-consultation booking window, activation at `FirstCompletedConsultation`, no-show credit handling through `CancellationPolicy`, and provider-cancellation credit restoration. Only `GeneralNutrition`, `WeightLoss`, `WeightGain`, and `HealthyLifestyle` are initially eligible. `Diabetes`, `PCOS`, `Pregnancy`, `ChildNutrition` and `SportsNutrition` can be configured only on a newly reviewed package content version; seeding never enables them automatically.

`DurationDays` is authoritative. `DurationWeeks` is retained for older clients and synchronized to ceiling(days / 7), so a 15-day configuration remains 15 days. A legacy weeks-only write is converted to days. Conflicting simultaneous day/week inputs and invalid values are rejected. Newly unspecified benefit counts/windows may remain zero in an incomplete draft. Publication requires a confirmed duration, initial consultation duration/count, valid follow-up duration when included, diet plan allowance, credit expiry, first-consultation window, tracking frequency, supported activation/no-show rules and eligible categories, plus English/Urdu names and an effective start date. Published credit expiry must be positive and cannot exceed the package duration; an existing enrollment can be extended separately through the audited Admin action.

The exact package contract adds `durationDays`, `initialConsultationCount`, `initialConsultationMinutes`, `followUpConsultationCount`, `followUpConsultationMinutes`, `dietPlanCount`, `dietPlanRevisionCount`, `progressTrackingFrequency`, `creditExpiryDays`, `firstConsultationWithinDays`, `eligibleServiceCodes`, `activationRule`, `noShowCreditRule`, `restoreCreditsOnProviderCancellation`, `nutritionistApprovedById`, `nutritionistApprovedAt` and `nutritionistApprovedVersion`. `nutritionistApprovedById` is the approving User ID, checked against that user's professionally verified Nutritionist profile and confirmed active account.

`POST /api/configuration/packages/{id}/nutritionist-approval` accepts `{ "approvalConfirmed": true, "rowVersion": "..." }` or the current `expectedVersion`. Only a professionally verified Nutritionist with a confirmed active account can perform it. The reviewed draft must be complete and have an effective start date. Approval does not publish or activate it. Administrative callers cannot create this approval through the review endpoint or by setting protected approval fields in a save request.

Draft edits and draft revisions increment the package content `version` and clear clinician approval. Publication checks that `nutritionistApprovedVersion` matches the exact current version and the reviewing clinician remains verified and active. Package publish/unpublish transitions retain content `version`; SQL `rowVersion` protects state changes. This avoids silently advancing a clinician's review to another content version. Every review, edit, publication and unpublication retains configuration history. Overlapping published packages with the same name are rejected.

Services have an optional `packageServiceCode`. Supported values are the nine care categories above plus `FollowUp` and `DietPlan`. Freshly created proposed services receive their corresponding tags. Existing service tags, including null, are never changed automatically by an upgrade; they require explicit staff configuration before package use. These tags identify eligible service type and do not approve a package or create credits.

Cancellation policies add `packageNoShowCreditAction` and `packagePatientCancellationCreditAction`, each limited to `ReviewRequired`, `Release` or `Consume`. Both default to `ReviewRequired` for proposed and existing configurations. No automatic no-show consumption, cancellation credit release or financial refund rule is invented by this configuration change. A separately approved policy and its booked snapshot govern the credit workflow. Existing refund/reschedule fields retain their meaning.

Versioned seeding uses the audited `Proposed package configuration v2` marker. A fresh database receives exactly three proposed package configurations with the full terms. A database already marked v1 receives three additional v2 drafts, preserving every existing package row, owner-edited price and approval/publication state. These drafts remain unpublished/inactive/unapproved. Restart does not recreate them or reset later edits. No seed enables package checkout.

The tracked EF migrations supply the new columns, primitive string-array mapping and approval User FK, with `ReviewRequired` defaults on existing cancellation rows. The SQL run verified fresh schemas and the checksummed backup/restore upgrade through all three tracked migrations. Recovery preserved the legacy Starter price of PKR 4250 and added three separate proposed v2 drafts, all unpublished. No public purchase endpoint is introduced by these configuration changes; package checkout remains disabled.

All 14 `PackageConfigurationRulesTests` and seven `SqlPackageConfigurationTests` cases passed. They cover incomplete draft/publication separation, day/week compatibility, invalid benefits and tags, default review-required credit actions, draft-only proposal values, v1 preservation/restart idempotence, non-nutritionist and unverified/inactive/unconfirmed denial, exact-version approval, protected fields, edit/revision invalidation, specialty re-review, approval deactivation and stale SQL row versions.

All four `SqlPackageEnrollmentHttpTests` cases also passed with real JWT sessions and SQL. Patients can list only their own enrollments; another patient's detail returns 404, Nutritionists are denied this support/self-service endpoint, and only Admin can extend validity. Extensions require a reason and current row version, preserve reason/actor/before/after history, update the appropriate active-expiry or first-consultation window, audit success/failure and reject stale retries without duplicate history. Enrollments/payments were synthetic test fixtures; these checks do not prove live provider checkout, refunds, full-stack staging journeys or clinician/Urdu translation acceptance.
